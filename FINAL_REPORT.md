# Итоговый отчёт — Dispatcher v3 «AI Multi-Agent Control Center»

Дата: 2026-07-17 · Ветка: `claude/multi-ai-control-center-xg2372` (default)

## 1. Что реализовано

### Транспорт `cli_session` — главное новшество
Dispatcher теперь управляет **официальными установленными CLI-клиентами через
уже выполненный вход пользователя** — ровно так, как если бы пользователь
запускал их вручную:

- **Обнаружение** (`app/cliagents.py`): бинарники (PATH + известные каталоги),
  версии, статус аутентификации по официальным файлам сессий (для Codex — его
  же офлайн-команда `codex login status`), доступные модели и уровни
  рассуждений из **локальных кэшей самих CLI**. Никаких сетевых вызовов.
- **Адаптер** (`app/providers/cli_agent.py`), два режима:
  - *reasoning* — одноразовый headless-вызов с отключёнными инструментами
    записи (Claude/Grok: авто-отказ разрешений + запрет Edit/Write/Bash;
    Codex: `--sandbox read-only`) — для планирования, совета, ревью;
  - *native* — CLI сам реализует задачу в **изолированном git-worktree**
    своими инструментами (Claude/Grok: `acceptEdits` в пределах worktree;
    Codex: официальный `workspace-write`); собранный патч валидируется против
    PathPolicy на границе интеграции — записи вне зоны отклоняют патч целиком.
- **Политика аутентификации соблюдена строго**: API-ключи не запрашиваются и
  не сохраняются; файлы сессий не читаются и не копируются; никакой эмуляции
  браузера. Нет сессии — `doctor` честно говорит «выполни вход в официальном
  клиенте».

### `dispatcher` — консольный центр управления
`doctor` (диагностика: установка/вход/модели/готовность; `--probe` — живой
сквозной тест с явным предупреждением о расходе квоты), `council`, `route`,
`capabilities`, `reputation`, `memory`, `gui`. Все тексты — русские; у команд
есть `--json`.

### Слой интеллекта
- **Реестр способностей** (`app/capabilities.py`): 12 осей (coding,
  architecture, debugging, research, creativity, security_review,
  documentation, testing, refactoring, red_team, large_context, alternative)
  по семействам моделей; это экспертные приоры **с провенансом**, неизвестные
  модели получают честный нейтральный профиль.
- **Маршрутизация** (`app/routing.py`): классификация задачи (RU/EN),
  роль-взвешенные оценки × ограниченный множитель репутации; каждое решение
  объяснимо; роли совета не сваливаются на одну модель.
- **Репутация** (`app/reputation.py`): только наблюдаемые события (итог
  прогона, верификация, одобрение человеком, откаты), сглаживание Лапласа,
  множитель в границах ×0.85–1.15 — приоры корректируются, но не затираются.
- **Совет ИИ** (`app/council.py`): `solo` / `pair` / `council` /
  `full_council` (архитектор → атака red team → осуществимость → синтез
  ведущим), параллельные независимые мнения, честная фиксация отказавших
  участников, след решений (`decision_path`).
- **Граф памяти проекта** (`app/memory_graph.py`): SQLite-граф узлов
  (решение/проблема/решение-фикс/подход/урок/задача) и **связей с причинами**
  (`solved_by`, `rejected_for`, `supersedes`, …); итоги прогонов записываются
  автоматически; в промпты агентов подаётся компактный дайджест.
- **Журнал целостности контекста** (`app/ledger.py`): свидетельства
  (файлы/команды/тесты/вызовы моделей/разрешения) на каждый прогон; в отчёте —
  машинно-сгенерированный раздел свидетельств; `attest()` не даёт утверждать
  «репозиторий проверен» без записей.
- **Риск-скоринг изменений** (`app/risk.py`): детерминированные факторы
  (чувствительные пути, размер диффа, преобладание удалений, код без тестов,
  CI-файлы) → уровень low/medium/high в отчёте и диалоге одобрения.

### Интеграция в оркестратор
Память проекта — в контекст задачи; ledger пишется на всём пути (repo/branch/
commit/инструменты/тесты/вызовы); CLI-провайдеры участвуют как планировщики,
ревьюеры (читают интеграционное дерево read-only) и **нативные исполнители**;
опциональная критика плана red team (`council_planning`); риск и свидетельства
— в отчёте и payload'е одобрения; репутация и узлы памяти обновляются на
верификации, одобрении/отклонении и сбоях.

### Headless-прогон `dispatcher run`
Весь конвейер оркестрации (план → изолированные worktree → интеграция → ревью
→ верификация → риск → решение о публикации) из терминала, синхронно, без GUI.
Безопасная политика публикации (`decide_publication`): одобренный прогон
коммитит **только изолированную интеграционную ветку локально**; `--push`
нужен для отправки ветки и отклоняется при непройденной верификации;
частичная/непройденная верификация или высокий риск требуют `--yes`;
`--dry-run` прогоняет всё и не публикует ничего; целевая ветка не трогается
никогда. Флаги: `--mode`, `--providers`, `--project`, `--show-diff`, `--json`.

### Адаптивная эскалация
`execution_mode: adaptive` запускает одиночного исполнителя и при **провале
верификации** эскалирует до пары (исполнитель + ревьюер) в свежих изолированных
worktree, передавая сводку провала как указание, и повторяет попытку. Эскалация
честно отмечается в отчёте; исходное дерево между попытками не трогается.

### UI
Формы CLI-провайдеров без полей ключей: статус сессии, выбор модели из
обнаруженного списка (редактируемый), уровни effort по выбранной модели,
таймаут вызова, честная строка биллинга «включено в подписку»; «Проверить
подключение» для CLI не тратит квоту (проверка сессии). Ведущая модель и
вкладки — по динамическому списку провайдеров.

## 4. Проверки

- **pytest: 193 теста — все зелёные** (было 100). Ни один тест не ходит в
  сеть и не запускает реальные CLI: подпроцессы и HTTP замоканы, обнаружение
  работает на фиктивных HOME-каталогах; e2e-тесты `run`/эскалации используют
  реальный git с замоканными провайдерами и верификацией.
- **pyflakes: чисто** (app, tests, run.py).
- **Живая диагностика**: `dispatcher doctor` — 3 из 3 ГОТОВ.
- **Живой сквозной тест** `dispatcher doctor --probe`: реальные ответы через
  существующие сессии — claude 3.2 с, codex 11.4 с, grok 3.5 с (все «pong»).
- **Живой совет** `dispatcher council --mode full_council` над реальными CLI:
  конвейер архитектор (Claude) → red team (Grok) → осуществимость (Codex) →
  синтез (Claude) отработал полностью; Codex в режиме «только чтение» сам
  открыл код проекта и указал реальные дефекты `app/config.py` с номерами
  строк, синтез перепроверил спорные утверждения по коду; свидетельства (4
  вызова моделей) записаны в ledger, итог — в граф памяти проекта и в
  `~/.multi_ai_control_center/reports/`.
- **Живой headless-прогон** `dispatcher run --mode solo --providers claude_cli
  --dry-run`: реальный Claude CLI в native-режиме создал `hello.txt` в
  изолированном worktree, патч собран и показан, риск оценён как low, dry-run
  отклонил публикацию — исходный репозиторий остался нетронутым (только ветка
  `main`, без `hello.txt`, без чужих worktree/веток).

## 5. Исправленные дефекты

1. **Windows-баг интеграции патчей**: `Path.write_text` без `newline="\n"`
   переводил LF→CRLF в файле патча, и `git apply` не находил контекст для
   изменённых файлов. Исправлено + регрессионный тест снова зелёный.
2. **Упаковка**: `packages=["app"]` не включал подпакеты (`app.providers`,
   `app.security`, `app.ui`) в не-editable установку. Исправлено.
3. `--probe` больше не ломает JSON-вывод `doctor --json`.
4. **Найдено живым советом ИИ и подтверждено** (замкнутый цикл council → fix):
   запись `config.json` была неатомарной (обрыв на середине терял конфиг) —
   теперь temp-файл + `replace`; битый `config.json` молча заменялся
   дефолтами — теперь он сохраняется как `config.json.corrupt-<ts>`.
   Оба исправления с регрессионными тестами.

## 6. Ограничения (честно)

- **Квоты подписок не видны**: CLI их не раскрывают; Dispatcher показывает
  «не раскрывается провайдером», а расход токенов — только там, где CLI его
  отдаёт (Claude — да; Codex/Grok headless — нет, показывается 0).
- **Steering во время native-вызова** невозможен: один вызов CLI атомарен;
  указания, отправленные до старта, включаются в промпт, остальные — со
  следующей задачи.
- **Форматы вывода CLI** могут меняться между версиями; парсинг защитный
  (JSON → сырой текст), проверенные версии зафиксированы, `--probe` даёт
  быстрый сквозной контроль.
- Headless `dispatcher run` реализован через синхронный вызов оркестратора
  (DirectConnection сигналов), но сам оркестратор всё ещё класс QThread —
  полная развязка от Qt (для запуска на сервере совсем без PySide6) остаётся
  на будущее.
- PathPolicy для native-режима применяется на границе интеграции, а не на
  каждой записи внутри worktree (изоляция worktree + отклонение патча целиком
  покрывают риск; описано в SECURITY.md).
- Оценки реестра способностей — экспертные приоры (с провенансом), а не
  бенчмарки; они корректируются измеряемой репутацией.

## 7. Рекомендации — что делать дальше

1. Встроить многораундовый совет в конвейер реализации (вердикт совета → план
   → реализация → перекрёстное ревью) — `council.py` уже переиспользуем.
2. Расширить эскалацию за один шаг (solo → pair → full_council) и сделать
   лестницу эскалации настраиваемой.
3. Полностью развязать оркестратор от QThread (запуск на сервере без PySide6);
   учёт квоты по числу вызовов (раз токены скрыты подпиской).
4. Браузер графа памяти в UI; богатая приборная панель прогона (граф задач).
5. Докеризация native-шага для строгой сетевой изоляции CLI-агентов.
6. Периодически запускать `dispatcher doctor --probe` после обновлений CLI —
   это самый дешёвый способ поймать смену форматов вывода.
