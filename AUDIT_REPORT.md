## 2. Сильные стороны

1. **Модель безопасности** — лучшая часть проекта: 30 явных критериев приёмки
   (см. `IMPLEMENTATION_STATUS.md`) выполнены; исходное дерево пользователя
   технически не может быть испорчено (worktree-изоляция, запрет `git add -A`,
   явный approval-gate, откат).
2. **Честность интерфейса**: биллинг ≠ rate-limit ≠ квота; неизвестные данные
   помечаются «нет данных», а не выдумываются; редакция секретов повсюду.
3. **Архитектурная чистота**: транспорт-нейтральное ядро (`make_adapter`,
   нейтральные Message/ToolSpec), оркестратор не ветвится по имени провайдера —
   добавление нового транспорта не трогает ядро.
4. **Дисциплина тестов**: 100 тестов без единого сетевого вызова; e2e-прогон
   доказывает неприкосновенность исходного дерева.

## 3. Слабые стороны (закрывает v3)

1. **Главный пробел — нет доступа к подписочным агентам.** Транспорт
   `subscription_agent` — заглушка «недоступно». Пользователь платит за Claude
   Code (Opus), Codex (ChatGPT) и Grok Build (SuperGrok), но Dispatcher требует
   API-ключи с пер-токенной оплатой. Решение v3: транспорт `cli_session` —
   официальные установленные CLI с уже выполненным входом, запускаемые как
   подпроцессы (ровно так, как их запускает пользователь вручную).
2. **Нет headless-режима**: `dispatcher` запускает только GUI; нет `doctor`,
   нет консольного «совета» (council).
3. **«Совет» примитивен**: `full_council` = «все исполнители параллельно»;
   нет многораундового процесса (предложение → атака → осуществимость → синтез).
4. **Нет реестра способностей моделей** — маршрутизация задач опирается на
   строку `strength`, а не на структурированные оценки (coding / architecture /
   red_team / …), и не объяснима.
5. **Нет репутации агентов** — прошлые успехи/провалы не влияют на выбор.
6. **Нет памяти проекта** — решения, ошибки и отклонённые подходы не
   сохраняются структурированно (только сырые события прогонов).
7. **Нет журнала целостности контекста** — отчёт агента может утверждать
   «я проверил репозиторий», и это не сверяется со свидетельствами.
8. **Нет риск-скоринга изменений** — approval-диалог показывает дифф и
   верификацию, но не оценку риска (чувствительные пути, объём, удаления).
9. Упаковка: `[tool.setuptools] packages=["app"]` не включает подпакеты
   (`app.providers`, `app.security`, `app.ui`) в не-editable установку.

## 4. Найденные и исправленные дефекты

1. **Windows-баг интеграции патчей** (`workspace.py:apply_patch`):
   `Path.write_text` без `newline="\n"` переводил LF→CRLF в файле патча;
   `git apply` не находил контекст для изменённых файлов (новые файлы
   проходили). На Linux-CI не воспроизводился. Исправлено (`newline="\n"`),
   тест `test_conflicting_patches_reported` снова зелёный на Windows.

## 5. Риски эволюции v3 (и принятые меры)

| Риск | Мера |
|---|---|
| Форматы вывода CLI меняются между версиями | Парсинг defensively (JSON → fallback на сырой текст), фиксация проверенных версий в реестре обнаружения, `dispatcher doctor --probe` для сквозной проверки |
| Долгие вызовы (max/ultra effort) | Настраиваемые таймауты на вызов, отмена с убийством дерева процессов |
| Лимиты подписок не видны программно | Честная пометка «квота не раскрывается провайдером», без выдуманных чисел |
| Native-режим (CLI сам редактирует файлы) обходит PathPolicy на записи | Изоляция worktree сохраняется; патч агента валидируется против PathPolicy на границе интеграции; секретные пути (deny-глобы) отфильтровываются всегда |
| Windows: npm-шимы (`claude.cmd`), пути | Обнаружение через `shutil.which` + известные каталоги; запуск без `shell=True` |
| Русскоязычные отчёты при английских выводах CLI | Слой отчётов Dispatcher — русский; сырые выводы агентов цитируются как есть |

## 6. Дорожная карта v3 (эта сессия)

1. **Фундамент CLI-провайдеров**: обнаружение (`claude` 2.1.211, `codex` 0.144.5,
   `grok` 0.2.101 подтверждены на машине), статус аутентификации по официальным
   файлам сессий, доступные модели/efforts из локальных кэшей CLI;
   `dispatcher doctor`.
2. **Адаптер `cli_session`**: reasoning-вызовы (`claude -p --output-format json`,
   `codex exec`, `grok -p --output-format json`) + native-режим исполнителя в
   изолированном worktree.
3. **Слой интеллекта**: реестр способностей (с провенансом), объяснимая
   маршрутизация, репутация агентов, «совет» solo/pair/council/full_council
   (архитектор → red team → осуществимость → синтез).
4. **Память и целостность**: граф памяти проекта (SQLite, узлы/рёбра с
   причинами), журнал свидетельств контекста, риск-скоринг изменений.
5. **UI + документация + релиз**: настройки CLI-провайдеров (модель/effort на
   участника), README/PROVIDERS/ARCHITECTURE, `FINAL_REPORT.md`, полный прогон
   тестов, pyflakes, живой smoke `doctor`/`council`, коммит и push в default-ветку.

Дефолтные модели (подтверждены локальными кэшами CLI): Claude —
`claude-opus-4-8`, effort `max`; Codex — `gpt-5.6-sol`, effort `ultra`
(максимальный из поддерживаемых уровней); Grok — `grok-4.5`, reasoning `high`
(максимальный у провайдера). Для каждого участника модель и effort выбираются
независимо из обнаруженного списка.
